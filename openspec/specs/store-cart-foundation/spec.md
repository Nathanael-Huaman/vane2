# Store Cart Foundation Specification

## ADDED Requirements

### Requirement: Cart persistence model

The system MUST persist a base shopping cart and cart items in Prisma.

A cart MUST be able to represent:

1. an anonymous shopper identified by a server-generated cart token; and
2. an authenticated shopper linked to a `Usuario`.

Cart items MUST link one cart to one product and quantity. A cart MUST NOT contain duplicate line items for the same product.

#### Scenario: Anonymous cart can be persisted

- **Given** a visitor has no active cart
- **When** the visitor adds a product to cart
- **Then** the system MUST create a cart record
- **And** the cart MUST be addressable by a server-generated anonymous cart token
- **And** the cart MUST contain one item for the selected product

#### Scenario: Authenticated cart can be persisted

- **Given** a signed-in user has no active cart
- **When** the user adds a product to cart
- **Then** the system MUST create a cart record linked to that user
- **And** the cart MUST contain one item for the selected product

#### Scenario: Product line uniqueness is enforced

- **Given** a cart already contains product `A`
- **When** the shopper adds product `A` again
- **Then** the cart MUST update the existing line quantity
- **And** the cart MUST NOT create a duplicate line for product `A`

### Requirement: Anonymous cart cookie handling

The system MUST store anonymous cart identity in an httpOnly cookie or equivalent server-only mechanism.

The anonymous cart token MUST be generated by the server and MUST NOT require client-side local storage.

#### Scenario: Anonymous add creates server-side identity

- **Given** a visitor has no cart identity
- **When** the visitor adds an item to cart
- **Then** the server MUST issue a cart identity cookie
- **And** subsequent cart reads MUST use that identity to load the same cart

#### Scenario: Missing or invalid cart identity returns empty cart

- **Given** a visitor has no valid cart identity
- **When** the visitor opens `/carrito`
- **Then** the page MUST render an empty cart state
- **And** no cart mutation MUST occur just from reading the page

### Requirement: Product purchasability validation

Cart write operations MUST only accept products that are currently purchasable.

A purchasable product MUST:

1. exist;
2. have status `active`; and
3. have `stockQuantity` greater than zero.

Active out-of-stock products MAY remain visible in the public catalog/detail routes, but MUST NOT be addable to cart.

#### Scenario: Active in-stock product can be added

- **Given** a product exists with status `active`
- **And** its stock quantity is greater than zero
- **When** a shopper adds quantity `1` to cart
- **Then** the cart mutation MUST succeed
- **And** the cart MUST contain that product with quantity `1`

#### Scenario: Draft product cannot be added

- **Given** a product exists with status `draft`
- **When** a shopper attempts to add it to cart
- **Then** the mutation MUST be rejected
- **And** the cart MUST NOT contain that product

#### Scenario: Archived product cannot be added

- **Given** a product exists with status `archived`
- **When** a shopper attempts to add it to cart
- **Then** the mutation MUST be rejected
- **And** the cart MUST NOT contain that product

#### Scenario: Active out-of-stock product cannot be added

- **Given** a product exists with status `active`
- **And** its stock quantity is `0`
- **When** a shopper attempts to add it to cart
- **Then** the mutation MUST be rejected
- **And** the public product detail route MAY still render the product as visible but unavailable

### Requirement: Cart quantity validation

Cart mutations MUST validate item quantities server-side.

Quantity MUST be a positive integer for add/update operations and MUST NOT exceed current product stock.

#### Scenario: Quantity greater than stock is rejected

- **Given** a product has stock quantity `2`
- **When** a shopper attempts to set cart quantity to `3`
- **Then** the mutation MUST be rejected
- **And** the cart line MUST NOT exceed quantity `2`

#### Scenario: Non-positive quantity is rejected for add

- **Given** a product is purchasable
- **When** a shopper attempts to add quantity `0` or less
- **Then** the mutation MUST be rejected

#### Scenario: Update quantity succeeds within stock

- **Given** a cart contains product `A` with quantity `1`
- **And** product `A` has stock quantity at least `3`
- **When** the shopper updates the line quantity to `3`
- **Then** the cart line quantity MUST become `3`

### Requirement: Remove and clear cart items

The system MUST allow shoppers to remove individual line items and clear all items from the current cart.

#### Scenario: Remove item deletes one cart line

- **Given** a cart contains product `A` and product `B`
- **When** the shopper removes product `A`
- **Then** the cart MUST still contain product `B`
- **And** the cart MUST NOT contain product `A`

#### Scenario: Clear cart removes all lines

- **Given** a cart contains one or more line items
- **When** the shopper clears the cart
- **Then** the cart MUST have no line items
- **And** `/carrito` MUST render the empty cart state

### Requirement: Live price subtotal

The cart MUST calculate line totals and subtotal from current product prices in integer minor units.

The cart MUST display money using the existing Peruvian soles formatting convention.

This slice MUST NOT create immutable order-price snapshots.

#### Scenario: Subtotal uses current product price

- **Given** a cart contains product `A` with quantity `2`
- **And** product `A` has current price `12000` minor units
- **When** the cart summary is calculated
- **Then** the line total MUST be `24000` minor units
- **And** the subtotal MUST include `24000` minor units for that line

#### Scenario: Subtotal is formatted in soles

- **Given** the cart subtotal is `24000` minor units
- **When** `/carrito` renders the subtotal
- **Then** it MUST display the amount using the `S/.` soles format

### Requirement: Add-to-cart UI on product detail

The public product detail route `/tienda/[slug]` MUST expose an add-to-cart affordance for purchasable products.

The route MUST show unavailable messaging instead of an add action for active out-of-stock products.

#### Scenario: In-stock detail page shows add-to-cart

- **Given** a product exists with status `active`
- **And** stock quantity is greater than zero
- **When** a shopper opens `/tienda/<slug>`
- **Then** the page MUST show an add-to-cart action

#### Scenario: Out-of-stock detail page blocks add-to-cart

- **Given** a product exists with status `active`
- **And** stock quantity is `0`
- **When** a shopper opens `/tienda/<slug>`
- **Then** the page MUST indicate the product is unavailable for cart
- **And** the page MUST NOT submit a successful add-to-cart mutation

### Requirement: Cart page UI

The route `/carrito` MUST render the current cart for anonymous and authenticated shoppers.

The cart page MUST support:

- empty state;
- line item display;
- quantity update;
- line item removal;
- clear cart;
- subtotal display.

#### Scenario: Empty cart renders empty state

- **Given** a shopper has no cart items
- **When** the shopper opens `/carrito`
- **Then** the page MUST render an empty cart state

#### Scenario: Cart page renders line items and subtotal

- **Given** a shopper has a cart with product `A`
- **When** the shopper opens `/carrito`
- **Then** the page MUST show product `A`
- **And** the page MUST show product quantity
- **And** the page MUST show line total or enough information to verify subtotal
- **And** the page MUST show cart subtotal

#### Scenario: Cart page updates quantity

- **Given** a shopper has product `A` in cart with quantity `1`
- **When** the shopper updates quantity to `2` on `/carrito`
- **Then** the page MUST reflect quantity `2`
- **And** subtotal MUST update accordingly

#### Scenario: Cart page removes item

- **Given** a shopper has product `A` in cart
- **When** the shopper removes product `A` on `/carrito`
- **Then** product `A` MUST no longer appear in the cart

### Requirement: Server action response and revalidation

Cart mutations MUST use the existing action response shape: success responses with `{ ok: true }` and error responses with `{ ok: false }` semantics.

Successful cart mutations MUST revalidate the relevant cart UI.

#### Scenario: Add action returns success response

- **Given** a shopper adds a purchasable product
- **When** the server action completes
- **Then** it MUST return a success response
- **And** the cart page MUST be eligible for revalidation

#### Scenario: Invalid add action returns error response

- **Given** a shopper attempts to add a non-purchasable product
- **When** the server action completes
- **Then** it MUST return an error response
- **And** the product MUST NOT be added to cart

### Requirement: Existing catalog/admin behavior remains intact

The cart slice MUST preserve existing public catalog and admin product management behavior.

#### Scenario: Public catalog still shows only active products

- **Given** products exist in active, draft, and archived states
- **When** a shopper opens `/tienda`
- **Then** only active products MUST be publicly listed

#### Scenario: Active out-of-stock products remain visible

- **Given** an active product has stock quantity `0`
- **When** a shopper opens `/tienda` or `/tienda/<slug>`
- **Then** the product MAY remain visible
- **And** it MUST be marked unavailable for purchase

#### Scenario: Admin product management remains protected

- **Given** a non-admin shopper has cart access
- **When** the shopper attempts to access `/admin/tienda`
- **Then** admin product management MUST remain denied

### Requirement: Tests and strict TDD evidence

Implementation and verification MUST follow strict TDD protocol: RED, GREEN, TRIANGULATE, REFACTOR.

Coverage MUST include schema/service/action behavior, public UI behavior, anonymous cart identity, product purchasability, quantity limits, subtotal formatting, and regressions for catalog/admin behavior.

#### Scenario: RED evidence exists before implementation

- **Given** apply phase starts
- **When** validators/tests for cart foundation are added
- **Then** phase report MUST include failing RED evidence before production code changes complete

#### Scenario: Verification commands are recorded

- **Given** implementation is complete
- **When** verify runs
- **Then** verification SHOULD include targeted cart validators/tests
- **And** SHOULD include `pnpm lint`, `pnpm test`, and `pnpm build`
- **And** targeted Playwright SHOULD run through `scripts/run-e2e.mjs`

## Non-goals

The following are explicitly out of scope for `store-cart-foundation` and MUST NOT be implemented in this change:

- checkout;
- orders or order items;
- payment providers or payment states;
- shipping, tax, invoices, fulfillment, notifications;
- stock reservation, stock decrement, inventory locks, abandoned-cart recovery;
- discounts, coupons, bundles, variants, multi-currency;
- admin order/cart management;
- merge-on-login behavior;
- catalog-card add-to-cart buttons unless separately approved;
- broad storefront/navbar redesign.
